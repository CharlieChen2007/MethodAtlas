## 1. 问题 6：上传新论文无法解析 —— 六个问题的回答 + 修复

### 1.1 修复前的真实链路（逐环实测，不是推测）

| # | 用户的问题 | 实测答案 |
|---|---|---|
| **Q1** | 上传按钮调什么函数？ | `RightToolbar「＋上传论文」` → 隐藏 `input[type=file][id=lab-upload-input]` → `LabShell.handleUpload(file)` → **Server Action** `uploadPaper(fd)`（`src/app/projects/[pid]/workspace/actions.ts:17`） |
| **Q2** | 调哪个后端？ | Python `parser-service/`，具体是 `POST {PARSER_SERVICE_URL}/parse` |
| **Q3** | parser-service 启动了吗？ | **没有**。`ps` 为空；`curl 127.0.0.1:8000` 返回 `000`（连不上） |
| **Q4** | `PARSER_SERVICE_URL` 指向哪？实测能通吗？ | `.env` 里是 `http://127.0.0.1:8000`。默认不通；**手动起服务后能通**（`/health` → `{"status":"ok"}`；`/parse` 能返回 title/authors/year/pageCount/paragraphs） |
| **Q5** | 完整链路是什么？ | **断在中间**：上传只写了 `rawText` 就停在 `PARSED`，**从未调用** `extractMethodDNA`。铁证：论文 `cmu74f31j…` 卡在 `PARSED`，而种子论文都是 `DNA_EXTRACTED` |
| **Q6** | 降级方案是什么？ | **完全没有**。失败路径是 `catch { console.error(...); status = FAILED }` —— **静默失败**，用户界面上看不出任何东西 |

**一句话根因**：链路依赖一个**默认没起**的外部 Python 服务，且失败被静默吞掉；
就算服务起了，链路本身也**缺最后一步**（不抽取方法 DNA）。

### 1.2 修复方案（B1：内置解析）

| 改动 | 文件 | 作用 |
|---|---|---|
| 新增纯 Node PDF 解析 | `src/lib/pdf-parse.ts` | 把 `parser-service/main.py` 的启发式**移植**过来（段落切分 / 标题 / 摘要抽取），用 `pdfjs-dist` 在 Node 里直接解析，**不再依赖外部服务** |
| 新增上传 API Route | `src/app/api/upload/route.ts` | `POST /api/upload`，`runtime='nodejs'`；完整链路：校验 → 建 Paper(UPLOADED) → 写文件 → `parsePdf` → PARSED → **`extractMethodDNA`** → DNA_EXTRACTED |
| 上传改走 fetch | `src/components/lab/LabShell.tsx` | `handleUpload` 从 Server Action 改为 `fetch('/api/upload')`，读结构化 JSON，**每一步都有真实进度与明确错误** |

> 为什么 B1 而不是"把 Python 服务打包进来"：单窗口、无跨进程调用、
> 失败原因能直接返回给前端 —— 这正是 Q6 要的"降级方案"。

### 2.3 关键设计决策：为什么面板要选「手术记录」而不是「Block」

第一轮实测发现一个**真 bug**：剪刀点完 Block 后，面板显示的是 **Block 卡片**
（模块描述 / 在方法中的角色），一句话结论根本没出现。

根因：`handleSurgeryPick` 跑完手术选中了 `block-<id>`，于是渲染 Block 卡片。
而结论挂在 **Surgery 记录**上。修法两步：

1. 选中 `surgery-<id>`（等 RSC 刷新落地后用 effect 解析最新手术 id）；
2. `buildPanelContent` **按 id 前缀提前兜底**：只要选中 id 是 `surgery-`，
   直接渲染手术面板，不依赖画布 layout 里有没有这个节点。

> 顺带把节点 id 前缀收敛到 `node-ids.ts`：生成方（layout）与解析方（panel）
> 用同一个常量，不会再因为抄字面量而对不上。

## 3. 问题 5：击穿测试 → 给结论，不是给报错

### 3.1 用户要求

> 每项给 **通过/警告/失败** + 一句话理由 + 修改建议；
> 末尾总体判定 **可行/需要调整/不建议做**；**mock 模式也给诚实判定**。

### 3.2 修复前的问题

面板把模型的原始检查项**原样贴出来**：

```
演示模式无法检索新颖性
演示模式不具备检索与机制推理能力，无法对这一项做出真实判断。…
```

—— 这是**报错**，不是结论。用户读完不知道：这项过没过、该做什么、这个想法能不能做。

### 3.3 改动清单

| 改动 | 文件 | 作用 |
|---|---|---|
| 新增结论层 | **新增** `src/lib/lab/crash-summary.ts` | ① `PASS/CONCERN/BLOCKER` → 通过/警告/失败；② 每项配一句话理由 + 改法；③ 汇总总体判定 |
| 保留全部发现 | `page.tsx` | 原来每项只取 `arr[0]` 会**静默丢弃**其余发现；现在全量带上 `allFindings` |
| 带出权威建议 | `page.tsx` | 从 findings JSON 取 `conditionsToProceed` / `isMockMode` / `verdictReason` |
| 面板改成结论优先 | `panel.ts` 的 `crashPanel` | 总体判定 → 逐项（档位+理由+改法）→ 下一步 → 补充发现 → 实验设计 → 致命弱点 |
| 卡片也「给结论」 | `view-layout.ts` | 卡片标签 `击穿测试 · 需要调整`（不再是「证据不足」这种模型语言） |

### 3.4 关键设计决策：mock 的「诚实判定」到底是什么

「诚实」≠ 给个好看的结论，也 ≠ 全都说"无法判断"。对演示模式，诚实的判定是
**「需要调整」**：

- 结构性检查**真做了**（模块是否跨论文）→ 不能判"不建议做"（那是假装查出了致命问题）；
- 结论性检查**确实没做**（没有检索能力）→ 不能判"可行"（那是吹）。

所以演示模式统一落 **「需要调整」**，并明确写出"改哪一步能让判定变可靠"
（配置真实模型后重跑）。

判定优先级（`decideOverall`）：

```
有 BLOCKER            → 不建议做
演示模式              → 需要调整（并说明为什么既不能说可行也不能说不可行）
模型明确否定          → 不建议做
有警告项              → 需要调整
证据不足              → 需要调整（"没找到反证"≠"想法成立"）
全部通过              → 可行
```

### 3.5 实测结果

```
总体判定：需要调整
演示模式只完成了结构性检查（模块是否真的来自不同论文），没有做新颖性检索与机制推理
—— 所以既不能说"可行"，也没有依据说"不可行"。

四项检查 · 0 通过 / 4 警告 / 0 失败

[警告] 新颖性
演示模式没有联网检索与机制推理能力，这一项没有真正检查（不代表没问题，只代表还没查）。
改法：先做一次针对性查重：用本方案的核心组合（模块 A + 模块 B）去检索近两年的相关工作…

[警告] 模块冲突 … [警告] 数据可行性 … [警告] 算力可行性 …
```
