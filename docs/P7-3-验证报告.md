## 三、本轮修掉的 2 个真实产品 Bug

这不是脚本问题，是**产品本身的缺陷**，被这一轮验证逼出来的：

### Bug 1：被手术干预的 Core Method 节点**不会变红**

- **现象**：跑完方法手术，回到 DNA 视图，画布上看不出哪块被动过。
- **根因**：`CanvasNode.tsx` 的状态判断是 `if/else if` 链，
  **`isCore` 排在 `intervened` 前面**。而最常被拿来做手术的恰恰是
  Core Method 列（那是方法的命门），于是红框被深蓝边框"吃掉"。
- **修复**：把 `intervened` 提到 `isCore` 之前 ——
  "被干预"是比"是重心"更具体、更该被看见的状态，优先级更高。
- **实测**：修复前 `标记 1 / 标红 0`；修复后 `标记 1 / 标红 1` ✅

### Bug 2：React 「conflicting style property」警告

- **现象**：每次重渲染都报
  `Warning: a style property during rerender … don't mix shorthand and non-shorthand properties`。
- **根因**：同一 style 对象里既写 `border`（简写，覆盖四边）
  又写 `borderLeft`（长写），两者覆盖关系不稳定。
- **修复**：改成**逐边表达**（`borderTop/Right/Bottom/Left` 四条各自赋值），
  彻底消除覆盖冲突。
- **实测**：修复前有警告；修复后遍历 6 视图 **console errors = []** ✅

## 六、脚本自身的两处收窄（不是删断言）

本着"量错的东西比不量更糟"，本轮把 3 条断言收窄到它们**真正成立**的范围：

1. **节点边框**：改读 `borderTopColor`/`borderTopWidth`，
   而不是 `borderColor` 简写 —— 只要有一边被单独覆盖，
   简写就返回 4 个值（`1px 1px 1px 3px`），跟单值比必然失败。
2. **被干预标红**：加了两步前置 ——
   (a) 轮询等 RSC 刷新落地（server action 是异步回来数据）；
   (b) 点空白**取消选中**（选中态蓝框优先级高于红框，这是设计如此）。
   然后同时校验 `data-intervened="1"` **且** `borderTopColor` 是红。
3. **手术空态预览**：把"会被脚本自己写入的易变数据"（Surgery 表）
   在开跑前重置 —— 否则第一次跑通过、第二次跑就会因为上次留下的
   Surgery 记录而假失败。**脚本现在可重复执行。**
