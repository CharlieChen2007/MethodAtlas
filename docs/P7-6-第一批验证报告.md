## 问题 1：PDF 解析失败（根因不是"扫描件"）

### 根因

`src/lib/pdf-parse.ts` 把 worker 路径设成了**裸 Windows 绝对路径**：

```
D:\MethodAtlas\methodatlas\node_modules\pdfjs-dist\legacy\build\pdf.worker.mjs
```

Node 的 ESM loader 会把它当成「模块说明符」，识别出协议是 `d:`（盘符被当协议名），
于是拒绝加载：

```
Only URLs with a scheme in: file, data, and node are supported by the default
ESM loader. On Windows, absolute paths must be valid file:// URLs.
Received protocol 'd:'
```

**验证**（实测脚本输出）：

| 写法 | ESM loader 判定 |
|---|---|
| 裸路径 `D:\...\pdf.worker.mjs` | 被拒收：不支持的协议 `d:` |
| `file:///D:/.../pdf.worker.mjs` | 可加载（协议 `file`） |

而原来的错误提示把**任何**解析失败都归因为"可能是扫描件"，让用户去转 OCR ——
方向完全错。

### 修法

1. **路径转 `file://` URL**：新增 `toFileUrl()`，Windows 上显式构造
   `file:///D:/...`（不依赖 `pathToFileURL` 在边界情况下的行为 —— 那条错误
   一旦发生就是"上传必失败"，且只在 Windows 暴露，代价太高）。
2. **兜底降级**：worker 定位失败时 `disableWorker: true` 走同进程解析，慢但能出结果。
3. **错误分层**：新增哨兵 `NO_TEXT_LAYER`
   - 解析**跑完**但 0 字符 → 「很可能是扫描件（纯图片）」+ OCR 建议
   - 解析**出错** → 「这不是'扫描件'问题，而是解析器本身报错」+ 让用户把错误发给开发者

### 验证

| 场景 | 结果 |
|---|---|
| 带文字层的正常 PDF（`rag-2020.pdf`） | ✅ 上传成功，`blockCount=8`、`evidenceCount=15` |
| 纯图片 PDF（无文字层，用于验证提示分层） | ✅ 正确提示「很可能是扫描件」而非报错 |

## 问题 2：所有 Block 的角色都是同一句话

### 根因

`llm-mock.ts` 里 role 是**写死的三选一模板**，与句子内容无关：

```ts
role: inferredType === 'OTHER'
  ? '【演示推断】从论文方法描述句中拆出的通用组件'
  : '【演示推断】从论文方法描述句中识别出的组件'
```

**实测数据库**：20 个 Block，**只有 2 种** role。

### 修法

新增 `src/lib/lab/block-role.ts`：

- `deriveBlockRole(sentence)`：从描述句提炼真实功能角色（9 条规则）
- 提炼不出 → 返回**空字符串**，前端显示「未抽取到角色信息」+ 说明句
  （集中在 `ROLE_EMPTY_HINT`，避免各组件各写各的）

**为什么抽成独立模块**：数据层（`llm-mock.ts`）和刷新脚本（`reseed-roles.mjs`）
共用同一份规则，**不会出现"代码更新了但脚本还用旧规则"**。

### 关键坑：规则顺序

第一版按「检索 > 编码 > 生成 > 训练 > …」排，结果大量误判：

| 句子 | 第一版误判 | 修正后 |
|---|---|---|
| `RAG-Sequence and RAG-Token both achieve state-of-the-art results` | 检索 | 用于验证方法效果的评测环节 |
| `introduce general-purpose fine-tuning recipe` | 检索 | 定义模型的训练目标与优化方式 |

**根因**：`retriev` 在 RAG 类论文里几乎无处不在 —— 它出现在句子里 ≠ 这句话在说"这个模块负责检索"。
修正：先排除「结果陈述句 / 评测句」，并让**训练**排在**检索**之前（训练句也常提 retrieval）。

### 验证

```
修复前：20 个 Block，2 种 role
修复后：20 个 Block，7 种 role

  8 个  负责从语料库中检索出与问题相关的段落
  4 个  基于编码结果生成最终输出
  3 个  用于验证方法效果的评测环节
  2 个  把输入文本编码成向量表示，供后续环节使用
  1 个  属于检索环节的一部分
  1 个  定义模型的训练目标与优化方式
  1 个  为生成的答案提供出处，使其可追溯
```

**界面实测**（点三个不同 Block）：

| Block | 显示的角色 |
|---|---|
| `retrieval-augmented generation (RAG)` | 基于编码结果生成最终输出 |
| `dense passage retriever (DPR)` | 把输入文本编码成向量表示，供后续环节使用 |
| `RAG architecture` | 基于编码结果生成最终输出 |

### 存量数据刷新

代码改了不会改库。新增 `scripts/reseed-roles.mjs`：

```powershell
node --experimental-strip-types scripts/reseed-roles.mjs --dry-run   # 先看会改什么
```

- 写完自动校验：库内不允许再有「演示推断」标记

## 问题 3：手术结论里的句子套句子

### 根因

`llm-mock.ts` 里 `lostCapability: info.role` —— 直接把问题 2 那句模板文案当成了
"失去的能力"，再被套进 `移除 X 后，方法不再具备「Y」的能力` 模板：

```
移除 X 后，方法不再具备「【演示推断】从论文方法描述句中识别出的组件」的能力
```

### 修法

1. **源头**：用 `deriveBlockRole(info.description)` 重新提炼 —— description 是原文句子，
   比 `role` 字段更原始可靠。
2. **结论模板**：分三种情况
   - 有具体功能 → `移除X后，方法的核心流程会断在这里——因为X负责Y。`
   - 没有功能 → `移除X的影响无法从当前数据推断——这篇论文里没有与该模块对应的消融实验，也没有可用的功能描述。`
   - 有 self-contained 结论 → 直接用，不二次包装
3. **兜底防线**：新增 `src/lib/lab/text-clean.ts` 的 `stripInlineMarkers()`

### 验证

| | 内容 |
|---|---|
| **修复前** | 移除…后，方法不再具备「**【演示推断】**从论文方法描述句中识别出的组件」的能力 |
| **修复后** | 移除该模块后，方法的核心流程会断在这里——因为它负责**基于编码结果生成最终输出**。 |

断言实测：`含「【演示推断】」= False`、`含演示模式= False` ✅

## 要求 B：统一的文案清洗函数

新增 `src/lib/lab/text-clean.ts`：

| 函数 | 用途 |
|---|---|
| `stripInlineMarkers(s)` | 剥掉 `【演示推断】` / `【通用描述】`，并清理因剥离产生的空括号对 |
| `hasInlineMarker(s)` | 检测残留（测试/CI 断言用） |
| `deepStripInlineMarkers(obj)` | **深度遍历任意嵌套对象**，所有 string 字段统一清洗 |

**关键设计**：`buildPanelContent` 改成包装器，出口处对整份 `PanelContent`
调用一次 `deepStripInlineMarkers`：

```ts
export function buildPanelContent(...) {
  const content = buildPanelContentRaw(...)
  return content ? deepStripInlineMarkers(content) : null
}
```

**为什么放出口而不是各 panel 里**：面板有 7 个分支、每份内容有十几个字符串字段，
逐个手写清洗必然漏。放出口 + 深度遍历，**将来新增字段自动受保护**。

**为什么不用笼统的 `/【[^】]*】/`**：论文原文引号里也可能出现方括号
（如 `【1】`、公式编号），一律剥掉会破坏证据的忠实性。所以只收录**已确认属于内部标记**的两个。
