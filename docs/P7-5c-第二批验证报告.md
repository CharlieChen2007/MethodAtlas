## 二、问题 3：方法演化改成「按问题组织」

### 改之前的问题

演化视图画的是 `Relation` 卡片，标题形如 **「论文 A → 论文 B」**——这是**抽象关系**，用户看到的是"谁引用了谁"，而不是"大家都在对付哪个问题"。产品要求改成：卡片标题 = **问题名**，副标题 = 多篇论文的演进脉络。

### 改法

| 文件 | 改动 |
|---|---|
| `src/lib/lab/problem-status.ts` | **新增**。状态推导层：`deriveProblemStatus()`（由 `Attempt.outcome` 推导 已解决/部分解决/未解决）、`buildEvolutionSubtitle()`（"3 篇论文 · 部分解决"） |
| `src/lib/lab/view-layout.ts` | `evolutionLayout` 从「按 Relation 组织」改成「按 ResearchDebt 组织」；卡片 id `problem-<debtId>`；tone 按状态取色 |
| `src/lib/lab/panel.ts` | **新增 `problemPanel()`**（四段式），**删除 `relationPanel`**；卡片路由 `case 'evolution'` 改指 `problemPanel` |
| `src/lib/lab/views.ts` | 演化的 `question` 改写；`getAvailability('evolution')` 计数从 `relations.length` 改为 `debts.length` |
| `src/lib/lab/workflow.ts` | `judge()` 里 `evolution` 判据从 relations 改为 debts（与 views 同口径） |
| `src/components/lab/LabShell.tsx` | **修死按钮**：「运行债务合成」原先返回"尚未接入前端入口"，实际服务端 `debtAction` 一直存在 → 真正接线 |

### 状态推导规则（保守优先）

```

有"成功"             → 已解决
有"部分成功"         → 部分解决
全"失败/引入新问题"  → 未解决
全"未说明"           → 部分解决
```

## 三、问题 4：组合想法改「用户主导」

### 改之前的问题

点「重新生成组合」→ 系统在全池里**自动配对** → 画布上出现几张想法卡片。用户全程是**旁观者**：不知道候选为什么是这几个，也不能说"我要 A 和 B、针对这条债务"。

### 改法：三栏工作台

```
┌──────────────┬────────────────────────┬──────────────────────┐
│ ① 要解决什么  │ ② 拿哪些模块来拼         │ ③ 生成组合            │
│   问题        │   （按论文分组）         │   已选模块 / 目标债务  │
│              │                        │   [跨论文警告]        │
│ ○ 债务1      │ 论文X ─ ○ 模块a         │   ┌──────────────┐   │
│ ○ 债务2      │        ○ 模块b         │   │  生成组合     │   │
│              │ 论文Y ─ ○ 模块c         │   └──────────────┘   │
│              │                        ├──────────────────────┤
│              │                        │ 已生成的想法（N）      │
│              │                        │ 卡片：来自… / 目标债务 │
│              │                        │       / 机制…        │
└──────────────┴────────────────────────┴──────────────────────┘
```

**三个刻意的设计决定：**

1. **默认推荐，但可改**：不预选任何东西 → 直接点「生成组合」= 系统按全池给建议（沿用原自动模式）；一旦勾选，严格按勾选来。两条路都在。
2. **跨论文约束前置**：一旦选的 Block 全来自同一篇论文，右侧**立刻**给警告，而不是等点完再被服务端拒绝——把校验成本从用户手里拿走。
3. **结果上下叠在右栏**（不是另起一栏）：点完"生成"，结果出现在正下方，视线不用横跨屏幕。

### 同时修掉的一个真回归

第一版曾把右栏工具栏**藏掉**让工作台吃满整行。实测发现：**在 idea 视图里没有任何按钮能切到别的视图**（脚本点不到"击穿测试"，用户同样点不到）。
→ 改回右栏保留（25%），工作台占 75%，三栏 + 右栏内上下叠。多出的宽度用"合并第 4 栏"来换，而不是牺牲可用性。

## 四、问题 1：上传按钮固定到画布左上角

### 改之前的问题

上传按钮在**右栏最底部**。两个毛病：

1. **语义错位**：右栏是"流程站点导航"（DNA/演化/债务…），上传是"对画布加料"的动作；
2. **可用性差**：右栏下部是可滚动的论文切换器，论文一多按钮就被顶出视口，用户找不到入口。

### 改法

做成画布**左上角**的固定图标按钮（`＋`），与右上角剪刀按钮**左右对称**——左加右减，都在画布上。

- `CanvasStage` 新增 `onRequestUpload` / `uploadPending` / `uploadNote` 三个 props，只负责"被点了"，真正的 file input 与 `/api/upload` 仍在 `LabShell`（数据单向：画布 → LabShell → input.click）。
- 右栏去掉上传按钮，只在上传中显示一行"正在解析 X…"状态（避免老用户找不到入口）。
- 右栏空出来的 `pending` 护身符转给论文切换器：上传/抽取进行中禁用切换，避免"读哪篇"与"写哪篇"错位。

### 验收证据

## 六、遗留问题 2：验收脚本自动回滚

### 之前的问题

> 「现在脚本跑完会往库里写数据（新论文 + 手术记录），需要手动清。」

旧做法是「跑前清表」——它有两个毛病：**① 破坏性**（原本库里有数据就被删了，不可接受）；**② 覆盖面窄**（只清它想到的表，上传写入的 Paper/DNA/Block/Evidence 根本没人清）。

### 改法：文件级快照 + 跑完还原 + 失败报错

```python
take_snapshot()      # 跑前：记 Papers/Surgeries 等计数 + 拷贝 dev.db + 拷贝 storage/
   ...               # 跑验收（会写库）
restore_snapshot()   # 跑完：还原 dev.db + storage，再校验计数与哈希
```

四个关键决定：

| 决定 | 理由 |
|---|---|
| **文件级**而非逐表 delete | 逐表清必须穷举表名与依赖顺序，漏一张就留垃圾（旧做法正是栽在这）；文件级是"原样搬回来"，无论写了什么都与跑前逐字节一致 |
| **storage 也要管** | 上传会把 PDF 落到 `storage/`，只回滚库会留下孤儿文件（库里没 Paper、磁盘上却有） |
| **还原后校验**（计数 + sha256） | "命令成功但结果不对"是最隐蔽的失败 |
| **失败必须抛错** | 回滚是"恢复原状"的最后一环；若失败却只打印 warn，用户会以为干净了，下次在脏数据上跑——最坏情况。所以任何一步失败 → 抛异常 → 非 0 退出，并打印备份位置供手动恢复 |

### 验收证据

**① 正常回滚**（每次跑完都验证）：
```
[基线] 论文 4 / 手术 0 / 关系 0 / 债务 1 / 想法 2
[基线] dev.db 已快照 · storage 已快照 · 备份于 /tmp/verify-baseline-xxx
   ...（跑完 162 条，期间写入了论文与手术记录）
[回滚] 已恢复基线：论文 4 / 手术 0 / 关系 0 / 债务 1 / 想法 2 ✓
```
跑完 `md5sum prisma/dev.db` = `0c41137ad8247eaae1de2ba7ad09acd7` —— **与基线逐字节一致**。

**② 失败路径**（故意破坏备份）：
```
OK: 回滚失败时确实抛错 ->
  回滚失败（环境可能仍是脏的）：
    - 还原 dev.db 失败：快照里的 dev.db 丢失
    手动恢复：把 /tmp/verify-baseline-xxx 里的 dev.db 与 storage 覆盖回项目
```

**③ 退出码**：断言全过 **且** 回滚成功 才 `exit 0`。回滚失败也算失败——因为它会污染下一次运行（假通过/假失败），比"某条断言没过"更严重。

**额外能力**：`python3 scripts/verify-local.py --keep-data` 可跳过回滚（调试用，会明确提示环境可能仍是脏的）。

## 九、已知边界与诚实说明

1. **演示模式**：组合想法与状态推导在无 `LLM_API_KEY` 时走"机械配对 + 模板化 why"，缺口是**没有实验支持**。卡片与面板都如实标注了这一点，没有把推断说成结论。
2. **状态推导是保守规则**：无 attempt → 「未解决」。若某条债务其实在别处被解决了但没登记 attempt，会显示为未解决——这是"宁可显示未解决也不谎报已解决"的选择。
3. **组合想法的 `mechanism` 取第一条 why**：多条目标债务时卡片只放得下一句；面板完整列出所有债务，机制段同样只展示第一条（后续可扩展为逐条）。
4. **回滚粒度是整个 dev.db**：若同一时间有别人在写库，回滚会覆盖其改动。单机/演示环境下无此问题；多写场景需要改用事务级隔离。
